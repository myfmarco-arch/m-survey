# 满意度与体验诊断

## 多场景服务体验

**适用**：一项服务由多个任务、场景和具体功能组成，团队需要定位体验问题。

**核心结构**：

```text
使用资格和最近体验
→ 整体评价
→ 一级体验方向
→ 实际使用场景
→ 场景评价
→ 场景内功能使用
→ 已使用功能评价
→ 具体问题
```

**关键设计**：

- 明确回忆的具体时间和最近任务，避免将长期印象与单次交易混合。
- 先用场景缩小范围，再进入具体功能。
- 高分追问优势，低分追问问题，不让所有人进入所有模块。
- 满意度用于评价和诊断，不直接代替真实留存、复购或任务成功数据。

## 分数段分流的写法

示例（人工构造，阈值以组织口径为准）：

```markdown
##### Q2.【满意方面】【Q1=9-10】您觉得这项服务哪些方面做得好？最多选 3 项。【多选，选项随机，最多选3项，必答】

##### Q3.【待改进方面】【Q1=1-8】您觉得这项服务哪些方面还可以做得更好？最多选 3 项。【多选，选项随机，最多选3项，必答】
```

Q2 和 Q3 的选项一一镜像，例如“到账快”对应“到账慢”。分流追问放在一级方向评分之后，不放在评分之前。

## 常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 先问“哪些方面不满意”，再给同样的方面打分 | 后面的打分被前一题带偏 | 先评分，再对低分方向追问原因 |
| 给 8 分的人问“不满意的原因” | 措辞与受访者感受不符，答案勉强 | 改为“还可以做得更好的方面” |
| 满意度矩阵中混入频率（“分数越高表示故障越少”） | 一张量表测两种东西 | 频率单独用频率等级问 |
| 并非人人用过的方面没有“无法评价” | 没用过的人被迫打分 | 提供“无法评价”，单独编码，不计入均值 |
