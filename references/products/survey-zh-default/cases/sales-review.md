# 新版本与卖点复盘

## 软件新版本上线复盘

**适用**：新版本上线后，评估更新认知、功能使用和体验是否符合预期。

**核心结构**：

```text
版本和使用时长甄别
→ 整体评价
→ 更新内容认知
→ 实际使用功能
→ 已使用功能评价
→ 低分原因和具体问题
→ 改进建议
```

**关键设计**：

- 只让已更新且达到必要使用时长的用户评价版本体验。
- 分开测量“知道”“用过”和“满意”。
- 功能评价只引用用户确认实际使用过的功能。
- 上线后只调查不能证明版本造成了行为变化；因果评估需要对照和更强设计。

## 卖点复盘的写法

```text
资格核验（版本、使用时长）
→ 整体评价（在任何卖点展示之前）
→ 卖点状态：不知道 / 知道但没有影响 / 知道且有影响
→ 有影响的追问吸引原因；没有影响的追问不吸引原因
→ 最主要的一个卖点
→ 用过的卖点评价体验
```

示例（人工构造）：

```markdown
##### Q8.【卖点状态】【ALL】以下是新版本的一些变化。购买这部手机之前，您对每一项的了解情况是？【矩阵单选，行随机，必答】

| 子题 | 行内容 | 程序标签 |
|---|---|---|
| Q8_r1 | 锁屏可以自由调整时钟字体和位置 |  |
| Q8_r2 | 两台手机登录同一账号后，来电和验证码会同步到两台手机 |  |

| 编码 | 选项细节 | 程序标签 |
|---:|---|---|
| 1 | 之前不知道 |  |
| 2 | 知道，但对我购买没有影响 |  |
| 3 | 知道，而且是吸引我购买的原因之一 |  |
```

## 常见错误

| 错误 | 后果 | 改法 |
|---|---|---|
| 先展示全部卖点，再问总体满意度 | 总体分被卖点提示抬高或拉低 | 总体评价放在卖点展示之前 |
| 卖点直接用宣传口号 | 受访者看不懂，或被评价词引导 | 改成可观察的功能描述；删去评价词 |
| 不吸引原因只有“用不上” | 分不清是传播问题还是产品问题 | 加入“看不懂是什么”“不相信实际效果和宣传一样” |
| 后台优化类卖点也让人打体验分 | 用户无法直接感知，分数没有意义 | 只测认知；体验用可感知的变化代理，并说明不能归因 |
| 只调查仍在使用新版本的人 | 已退回旧版本的人被排除，满意度偏高 | 说明这一偏差；需要时为退回用户另设短问卷 |
