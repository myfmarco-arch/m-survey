# 官方中文撰写规范

本规范只影响 `survey-zh-default` 的中文表达。它可被 overlay 替换。写题的通用方法见 [题目工艺](../../modules/knowledge/question-craft.md)，本文件只管中文怎么写。

## 问卷文字

- 使用简短、直接、受访者可理解的中文。一句话只问一件事。
- 同一对象和概念始终使用同一名称。同一功能不在一题叫“应用双开”、另一题叫“分身空间”。
- 明确对象、时间范围和使用场景。
- 使用“最重要”“最主要”时明确限选数量。
- 抽象概念第一次出现时给出简短定义或例子。
- 不向受访者展示内部指标名、研究假设、分析术语和程序语言。
- 删除不影响理解的套话、礼貌语和重复提示。

## 改写示例

| 问题 | 不好 | 更好 |
|---|---|---|
| 宣传文案 | 【智能调度】全链路负载监测，指令精算优化 | （不作为可评价的功能。用户无法直接感知后台调度，改问“和升级前相比，日常操作的流畅度有什么变化”，并说明不能归因到这项技术） |
| 宣传文案 | 新输入法：全新语音输入体验，润色成工整文案 | 输入法支持语音输入，并能自动去掉“嗯”“那个”等口语词，把文字整理通顺 |
| 双重提问 | 您觉得这项功能的速度和界面怎么样？ | 拆成两题：速度一题，界面一题 |
| 预设立场 | 购买平板时，您非常关注稳定性吗？ | 购买平板时，以下哪些方面是您重点比较过的？（多选） |
| 一个选项多件事 | 系统执行能力、内容生成能力和生态覆盖都很强 | 拆成三个选项，并改成可观察的描述 |
| 对象错位 | 您愿意推荐亲朋好友购买现在这款手机吗？（研究对象是系统） | 您愿意向亲朋好友推荐您手机上的这个系统吗？ |
| 写反 | 不满意列表中写“投屏连接稳定” | 不满意列表中写“投屏连接不稳定、容易中断” |
| 次高分的追问措辞 | （给 8 分的人）您不满意的原因是什么？ | 您觉得哪些方面还可以做得更好？ |

## 评分题

### 满意度（常用规范）

| 项目 | 规范 |
|---|---|
| 点数 | 1–10 分，10 个整数刻度 |
| 锚点 | 1 = 非常不满意，10 = 非常满意；只标两端，中间不挂文字 |
| 主指标 | Top 2 Box（T2B）：打 9–10 分的人数 ÷ 有效评分人数，报告时称“满意率” |
| 辅助指标 | 均值。均值只作辅助，结论和比较以 T2B 为准 |
| 分母 | 选“无法评价”的人不计入分母，也不计入均值 |
| 分流追问 | 9–10 分追问做得好的方面；1–8 分追问“还可以做得更好”的方面。两套列表一一镜像 |
| 适用范围 | 整体满意度、模块满意度、功能满意度。同一份问卷里的满意度题全部用这一规范 |

写法：

```markdown
##### Q1.【整体满意度】【ALL】总体来说，您对……有多满意？【评分，必答】

评分：1–10 分；1 = 非常不满意，10 = 非常满意
```

以下情况不套用这一规范：

- 已有追踪口径不同。例如上一波用 1–5 分，跨波比较时沿用上一波，见 [跨波次可比性](../../services/validation/tracking-comparability.md)。
- 使用标准量表，例如 NPS（0–10 分）、SUS、SEQ。保留原量表的点数和计分。
- 测的不是满意度，例如同意度、可能性、喜好、难易。它们按下面的通用规则选点数。
- 用户或组织另有规定。

手机端 10 分矩阵较宽。行数多时，每屏不超过 5 行，或改为逐行出示。

### 通用规则

- 评分说明写在标题下一行：`评分：1–10 分；1 = 非常不满意，10 = 非常满意`。
- 小数值表示负面，大数值表示正面。整份问卷方向一致。
- 只标注两端时，不在中间刻度挂与刻度不对应的文字。
- 常用两端锚点：

| 测量 | 低端 | 高端 |
|---|---|---|
| 满意度 | 非常不满意 | 非常满意 |
| 表现 | 非常差 | 非常好 |
| 难易 | 非常困难 | 非常容易 |
| 同意度 | 非常不同意 | 非常同意 |
| 可能性 | 完全不可能 | 非常可能 |
| 喜好 | 非常不喜欢 | 非常喜欢 |

满意度以外的评分，组织已有锚点和点数时，沿用组织口径；没有时，同一问卷内同类测量用同一点数。

## 常用特殊选项

| 语义 | 写法 |
|---|---|
| 其他 | 其他，请注明____ |
| 以上都没有 | 以上都没有 / 以上都没有遇到 |
| 不知道 | 不知道 / 说不清 |
| 不记得 | 不记得了 |
| 不适用 | 不适用 / 没有用过，无法评价 |

## 指令题写法

- “为确认您在认真阅读，本题请选择‘比较同意’。”
- 放在较长的矩阵中作为一行，或单独一题。语气平和，不写“测谎题”。

## 交付文字

- 先给结论，再给依据。研究简报放在方案文件开头，一屏内说清。
- 不罗列用户没问的方法。只在用户或需求方点名，或需求写法容易被误读成另一种方法时，用一两句说明为什么不采用。
- 审核任务先写可操作的问题和风险。
- 方法咨询说明成立前提和结论边界。
- 最终问卷不混入思考过程和工作日志。
- 验证规则标识（例如 `measurement.option-source`）只出现在审核报告中，从零设计和修改问卷的交付物中用中文说明问题即可。
- 简报写在方案文件开头，表格最多 6 行，每格一句话，只写结论不写理由。
- 需确认项只列问卷本身还没定的事项，写进方案文件，每项一句并写明谁来确认。
- 验证记录、规则标识、假设清单和工作过程不写进交付物；审核报告例外。
